# D1｜基线、首次 GLM 复核与实例尝试账本

版本 v1.0｜2026-11-17｜对应 [10 实施方案](10_ReAct主导的证据优化与语义DAG实施部署方案.md) v1.3 §九 D1。本文区分代码实现、离线验证与线上效果。

## 1. 架构分析与实施取舍

方案的主线是合理的：先解决“证据是谁的、是否已经尝试过、首次合法动作是否可达”，再优化区分问题、上下文和执行调度。ReAct 继续负责调查方向和停止；语义 DAG 是后续执行机制，不是 D1 的必选依赖，也不能恢复提前写死未来 crop/tool 的旧短计划。边界详见 [09 §1、§7](09_DAG与旧短计划边界.md)。

D1 保留方案 A：自动准备、required 分割与自动测量继续按现有配置执行。自动动作同样需要审计，不应因为“不问模型”就不记录尝试。新增账本不会把“已尝试”变成“已确认”，也不会新增分割或尺寸资格。

实施时进一步限定：

- 实例物理身份使用原图 SHA 与原图坐标，不包含药材候选名或 crop 文件名。
- D1 只确定性合并精确坐标；高 IoU、包含关系、父 crop 的歧义关联属于 D2。本批没有把 0.85 IoU 当成可靠真值。
- 同实例可有不同输入版本；尝试键还需绑定像素、几何、方法/配置版本和相关身份、标定、mask/资格依赖。
- 索引是可重建的内部运行状态，不增加第二份跨阶段契约，不替代 `contracts.py`、证据 CAS 或原规则引擎。
- 既有原图、历史运行、模型、API 配置均未修改；新在线运行不复用历史实验快照。

## 3. 现在如何运行

```text
原图 → YOLO → CNN 分类
  ├─ CNN 可采信 → 继续原有合法分割/测量路径
  └─ CNN pending_review → 允许首次 classify_target GLM
        ├─ 成功 → 原有身份/分割/测量门处理
        └─ 不可辨认、other 或执行失败 → 保留实际结果，不因换名自动重发

每次单实例 classify_target/segment_instance/measure_instances 提议和预约：
绑定原图 SHA/实例 → 输入/方法/参数指纹 → 查询 operations
  ├─ 同键 pending/done/failed → 不新增执行、不新增预算、不新增证据
  └─ 有效输入变化 → 仍需通过原合法动作、质量、标定与预算校验
```

每个新任务的 workflow 根新增 `instance_ledger.json`，关联 crop、classification、mask、measurement 及 attempts。执行权威仍是 `operations.json`：语义键与 pending 在同一 operations 锁内写入，终态也在此登记；索引可由它和证据快照重建。没有增加跨任务缓存。

CNN batch 的逐 crop 分类产物进入 classification 索引；批任务仍沿用原批量 operation 预约，不把 CNN pending_review 与单 crop GLM 复核合并成同一尝试。

复用记录保留原 operation/target 身份；不为新名字复制一份“独立支持”。同框的新像素可以形成新尝试，**不代表程序已证明这次修复有效**。后验收益与关联歧义仍属后续任务。

## 4. 验证方法与证据

证据统一在项目根 `results/ui_out/fusion/verification/D1_20261117/`，不提交原始运行工件。

1. 修改前先跑标准 `selftest`，保留 `baseline.log`：Windows 虚拟 TEMP 下原子替换产生 WinError 650；该结果不能作为模型或算法失败。
2. 将测试进程 TEMP/TMP 指向项目内短目录 `_t`，重跑 `baseline_short_temp.log`：380 项，13 failures、1 error、1 skipped；原 B 三组 59/21/125 断言通过。这是本次真实新基线，不沿用历史 383 项结果。
3. 定向验收 `d1_acceptance.log`：24 项通过（D1 新增 11 项、stage2 10 项、原有 3 项相关回归）。语法编译通过，未增加依赖或修改跨阶段契约。
4. 完整修改后回归和遗留问题以同目录 `verification.json` 与 `final_selftest.log` 为准。

最终结果：**391 项，390 通过、1 跳过，0 失败/错误；原 B 59/21/125 项断言全部通过**，总命令退出码 0。跳过项为缺失历史参考 case 的字段对拍，不是 D1 功能测试。没有真实 API 烟测；离线通过不代表生产效果已验收。

中间集成曾剩 3 项失败，保存为 `integration_before_fixture_alignment.log`。复核发现假规划器因旧强制覆盖配置拿不到 presence 动作，抛出 StopIteration，随后走 runtime_fallback；这不是已成功做过观察却没有反思。另一个测试原本期望 no_gain 建议，但被当前 supporting 建议合法覆盖。对齐测试前置后，`baseline_alignment_final.log` 的 3 项均通过；没有把真实反思能力不足的问题用新阈值掩盖。

统一复验命令仍为项目根：

```powershell
$env:TEMP = Join-Path (Get-Location) '_t'
$env:TMP = $env:TEMP
New-Item -ItemType Directory -Force -Path $env:TEMP | Out-Null
.venv\Scripts\python.exe -X utf8 -m TCM_Fusion.cli.main selftest
```

短临时路径是此环境的测试规避方式，不是已修复 Windows 长路径部署；未通过删测试、跳过离线功能或放松质量门取得结果。

## 5. 验收边界与后续

- 首次 GLM 可达、同实例换名不重发、pending/done/failed 可追踪：已有离线执行路径验证。
- 本批没有重新训练模型，没有调用真实 GLM/IGM，不声称药材识别改善、token 节省或线上时延下降。
- 任务内关联只覆盖精确坐标；新增 ROI 是否仍为同一实例、关联 ambiguous 和实例资格共享由 D2 完成。本批保守保留原证据门，不从别名自动授予身份。
- Reflection Controller、资格投影、语义 DAG、事件队列和并发单写者尚未实施；本批只建立后续所需的可信尝试记录。
