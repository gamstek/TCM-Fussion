# 00｜新手快速入门

同步版本 v7.0｜2026-11-17｜以当前 `TCM_Fusion` 代码为准。

如果你第一次接触这套系统，先读这一页，不需要先看长文档。

---

# 1. 这套系统在做什么

输入：

```text
1 张或多张药材显微图像
```

输出：

```text
可能的药材结论
+ 支持/反证它的显微特征
+ 不确定性和复核原因
```

系统不是“让模型看一张图直接说药材”。

它分成三层：

```text
A：根据图像先给可能的药材候选
B：寻找显微特征、测量尺寸、形成规则证据
C：Agent 决定下一步查什么，运行时校验能不能执行
```

---

# 2. 三层各自负责什么

| 层 | 通俗解释 | 不负责什么 |
|---|---|---|
| A | 给候选药材名单 | 不给显微特征框，不直接定论 |
| B | 检测、分类、分割、测量、规则评分 | 不决定先查谁 |
| C | Agent 在合法动作里选择下一步 | 不能伪造证据、不能绕过身份门 |

一句话：

```text
A 提供方向
B 提供证据
C 决定调查顺序
```

---

# 3. 一次运行的大致流程

```text
原图（N 张）
→ A：每图五折，各取 Top-K，得到候选药材
→ B：YOLO 初检
→ CNN stage2 分类 YOLO crop
→ 必要时 GLM 补扫/定位
→ 分割 + 测量
→ 原规则 decide
→ A/B 融合
→ final_assessment
→ output.json / report.md
```

当前标准路径是 fast（不再提供开关）：

```text
fast 为唯一标准路径；
fast_yolo_stage2 仅为历史配置兼容保留，恒为 true。
```

也就是：

```text
YOLO 先出框
→ CNN batch 分类
→ 只对缺失的 required feature 做有限 GLM 补扫
```

---

# 4. Agent 是什么

Agent 是：

```text
LangGraph ReAct
assess → think → act → assess
```

它每一轮：

```text
assess：根据环境/结果重新评分，生成合法动作和停止判断
think：模型从合法动作里选一个
act：执行工具，记录成功/失败
再 assess
```

模型不能：

```text
直接画框
直接写证据
绕过身份门
用自由文本覆盖正式评分
```

# 5. 当前最重要的设计参数

```text
fast（标准路径，无开关）
auto_measure_after_segment = true
suppress_repeated_measurement = true
candidate_group_verification = true

max_seconds = 2400
fast_fallback_max_features = 2
fast_fallback_max_locate_calls = 6
feature_scan_tile_policy = full
feature_scan_max_tiles = 4
feature_scan_concurrency = 2

supporting_probe_total = 6
supporting_probe_per_candidate = 2
```

含义：

```text
auto_prepare_stage
  detect 后自动 classify + 必要测量 + scene_check，不占 planning。

auto_required_measurement
  top/活动候选的 required crop 已验证且尺度有效时，
  自动 segment，并复用 auto_measure_after_segment 自动测量。

candidate_group_verification
  top required 满足后，只对竞争候选 required 做一次核验；
  阴性/未知后不扩散。

max_seconds
  单次 Agent 工作流预算为 2400 秒（40 分钟），
  不是最终评估的硬 kill。

supporting_probe_total / per_candidate
  控制 supporting 观察的总预算和单候选预算。
```

# 6. 必须理解的几个词

## `required`

候选成立必须满足的判据。

```text
required 缺失
→ 不能正式确认
```

## `supporting`

辅助判据。

```text
supporting 阳性可增加 support_count
但不是候选成立的唯一必要条件
```

## `evidence`

只有真实工具产生、通过校验的工件才是证据。

不是证据：

```text
模型文本
A 先验
假设状态
工具“看起来成功”
```

## `support_count`

正式支持的不同 feature 类数。

```text
同一 feature 多个实例 → 只算 1 类
不同 feature → 多类
```

默认：

```text
min_support_features = 2
```

只有 1 类时通常为 `insufficient_evidence`，  
除非满足 D8b 单类放行条件（高置信且已与第二名区分）。

## `formal_score` / `fused_score` / `provisional_score`

| 字段 | 含义 |
|---|---|
| `formal_score` | 正式规则分 |
| `fused_score` | A/B 融合排序分 |
| `provisional_score` | 暂定排序分，只影响调查顺序 |

`provisional_score`：

```text
不进入 formal_support_count
不等于正式确认
```

## `pending`

```text
发现了线索，但身份、质量或测量未完成
```

不是阳性，也不是阴性。

## `UNCAL`

```text
有特征，但缺少可信定量
```

## `NO_REF`

```text
有特征，但当前候选缺少参考量程
```

# 7. 身份门与测量门

## 身份门

```text
identity_required crop
→ 必须先 classify/身份确认
→ 未确认不得 segment/measure
```

高分 `det_score` 只影响定位优先级，  
**不能绕过身份门**。

## 分割门

```text
segment quality=valid
→ 可用于测量
```

`quality=review`：

```text
可以诊断/复核
默认不进入正式测量
```

同一 crop/区域 review 后，  
不会因为换 ROI 文件名就无限重试。

## 测量门

```text
合格 mask + 可信 px_per_um + 用途资格
→ 才能产生 μm
```

没有这些：

```text
保留 unknown
不伪造尺寸
```

# 8. 停止是怎么决定的

不要把它理解成“模型说停就停”。

系统区分：

```text
finish        = 正式结论
request_review = 人工复核
```

当前 `assess` 生成：

```text
stop_decision:
  can_finish
  can_review
  recommended_exit
  blockers[]
```

含义：

```text
can_finish=true
→ 允许正式收尾

can_review=true
→ 始终允许人工复核

blockers[].actionable=true
→ 还有合法动作可以解决

没有合法动作
→ 推荐 review
```

`request_review` 是正常出口，  
不是失败。

# 9. 共享搜寻账本

同一个图像问题不应因为候选不同而重复调用。

例如：

```text
白芍需要 fiber
G1 也需要 fiber
```

现在共享为：

```text
image + feature + presence
→ 一次观察
→ candidate_ids 多个消费者
```

候选名不是视觉请求的身份。

# 10. 运行一次测试

在项目根：

```powershell
.venv\Scripts\python.exe -X utf8 -m TCM_Fusion.cli.main multi-view `
  --source-dir TCM_Fusion/dataset/白芍4图 `
  --a-python D:/Anaconda/python.exe `
  --name 我的测试 `
  --json
```

如果 `source-dir` 没有 `input_proof.json`：

```powershell
.venv\Scripts\python.exe -X utf8 -m TCM_Fusion.cli.main multi-view `
  --source-dir TCM_Fusion/dataset/白芍4图 `
  --manifest TCM_Fusion/运行结果/_my_manifest.json `
  --a-python D:/Anaconda/python.exe `
  --name 我的测试 `
  --json
```

先做 dry-run：

```powershell
.venv\Scripts\python.exe -X utf8 -m TCM_Fusion.cli.main multi-view `
  --source-dir <dir> --a-python D:/Anaconda/python.exe `
  --dry-run --json
```

dry-run 不调用真实模型，  
不能证明远端 API 可用。

# 11. 结果看哪里

| 文件 | 看什么 |
|---|---|
| `output.json` | 最终对内输出、top_candidate、status |
| `final_evidence.json` | 正式证据、判据状态、支撑/反证 |
| `final_assessment.json` | 最终研判、是否回退 deterministic |
| `agent_verdict.json` | Agent 结论、ranking、margin |
| `fusion.json` | A/B 融合分 |
| `agent_trace.json` | 每轮 thought、动作、工具、token |
| `workflow/operations.json` | 实际工具调用和状态 |
| `workflow/ops/` | 每次工具调用的输入/输出/中间工件 |
| `report.md` | 人类可读报告 |

# 12. 最常见的误解

```text
1. 有 YOLO 框 ≠ 身份确认
2. 有 presence 阳性 ≠ 正式支持
3. 有 segment ≠ 有可用 mask
4. 有 mask ≠ 有可信 μm
5. 多个同 feature 实例 ≠ support_count 增加
6. provisional_score 高 ≠ 正式结论
7. fused_score 高 ≠ 准确率
8. 空扫描 ≠ 全样本不存在
9. 服务失败 ≠ 阴性
10. final_assessment 是模型 ≠ 模型可以覆盖正式规则
```
