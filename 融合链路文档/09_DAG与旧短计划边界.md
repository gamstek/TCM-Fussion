# 09｜DAG 与旧“短计划”的边界

同步版本 v1.1｜2026-11-20

本文只解决一个问题：

> 现在引入 DAG / 局部执行图时，如何避免重新落回已经删除、且已被证明不可行的“短计划”。

## 单视野鉴别问题的授权入口

ReAct 可以选择一个当前判据问题，把取证范围限定在一张已标定原图。问题来自活动候选的知识库判据，主机同时绑定特征、形态问题、主判量纲、原图及标定摘要、证据版本和当前可见入口。模型在本轮选择 `problem_goal` 的 P 编号。D2 的角色是说明哪些候选使用这条证据，C 的串行 DAG 负责运行，D4 继续调度独立视野的物理动作。有 D4 分支待合并时，问题入口等待下一次规划。

以导管平均宽度为例。选择 P 后先在授权视野检查已有合格主判宽度，可以直接回传测量记录及摘要。已有唯一可核验裁图时直接绑定。两者均缺时，只有当本轮菜单实际提供该视野的导管 `feature_scan`，Agent 才能授权一次定向补扫。补扫按原分块额度扣费，空扫、部分完成、失败或实例歧义各有回执。另一个视野的导管不能完成这次授权。

唯一对象绑定后，原实例节点核验身份、取得掩码、检查标定和测宽用途、读取或执行测量。问题内的分割先交还 DAG 检查用途，即使模板已开启分割后自动测量。步骤、收尾预留、取消和失败仍受运行时约束。每种工具在一次授权内至多派发一次。主判字段、数值和测量来源均合格才返回物理证据。所需形态和药材间的区间辨析继续由原判据解释。

运行时在 `semantic_return.problem_result` 返回问题、视野、版本、实例、原因及合格测量引用，下一轮 ReAct 可据此选择其他对象、换视野或复核。语义计划写入既有 `semantic_plan.json`。按同一版本和视野已回交的问题会从本轮选项去重。

正式多图模板在 `agent.workflow` 同时启用 `semantic_execution` 和 `problem_goal_execution`，新任务使用 `adaptive_v2` 模型规划，ReAct 自行选择何时授权。配对基线使用同一模板的副本，仅将 `problem_goal_execution` 设为 `false`，经 `--config-template` 传入。旧模板缺少该字段时也沿用实例入口。真实标本的质量与全链路成本待下述盲测验收。[执行入口](../lib/agent/semantic_execution.py) · [闭环回归](../tests/integration/test_problem_goals.py)

### 配对验收口径

以标本为分组单位，冻结原图和视野顺序、专家标注的实例和易混负例、模型与权重、预算、并发、冷缓存策略。同一标本分别跑原 C＋D4 和开启问题授权的 C＋D4，交错两组顺序。导管与纤维双向计错。入组的漏检、无法辨认、失败和提前复核均保留。

| 指标 | 分母或计量边界 |
| --- | --- |
| 疑难召回 | 匹配真值框且身份正确的疑难实例数 / 全部标注疑难实例数；另列定位成功数以区分发现与核验收益。 |
| 混淆辨析 | 在两组相同的专家标注对象上，按混淆方向统计身份正确数 / 该方向全部对象数。同时报告无法判读数。 |
| 误认 | 困难负例误判为目标数 / 全部困难负例数，辅以每视野误检及错误药材确认数。 |
| 整案耗时、总 token | 从提交到终态交付，报告病例配对差值和尾部耗时。累加规划、视觉 worker、研判、失败与重试的实际 usage。缺报记为未知。 |

预先固定标本集合和统计方法。对标本的配对差计算单侧 95% 界，召回和辨析的改善下界须大于零，误认率、平均整案耗时和总 token 差的上界须小于等于零。分列普通标本与疑难标本。完整成本缺失或样本不足时，验收记为待验证。实测误认率、整案耗时或总 token 上升时，关闭问题授权。

## 1. 先给结论

```text
旧短计划 = 模型在观察前预生成具体工具调用序列
新 DAG   = 运行时按当前证据编译的语义任务依赖图
```

两者形似，但不是一回事。

如果新 DAG 由模型一次性写出：

```text
segment crop A
→ classify crop A
→ measure seg A
```

那它就是旧短计划的变体，不应重新引入。

---

## 2. 旧短计划是什么

旧设计大致是：

```text
模型看到当前上下文
→ 一次生成多个 supporting probe / 工具步骤
→ 执行器按计划连续执行
→ 被拒绝或证据变化后再回退
```

典型问题：

```text
计划在证据之前生成
target 在生成时写死
候选名进入计划
多个 probe 共享同一计划
执行时依赖/身份/预算已经变化
```

实际失败码包括：

```text
PLAN_SCOPE
PLAN_PROBE_DENIED
PLAN_NO_LONGER_LEGAL
```

最终删除原因不是“计划不够长”，而是：

```text
模型预规划的具体工具动作
跟不上运行时证据变化
```

---

## 3. 新 DAG 是什么

新 DAG 只承载“语义任务”和“依赖”：

```text
确认实例身份
→ 获取可用 mask
→ 检查测量用途资格
→ 测量
→ 更新判据
```

具体 target 不在计划生成时绑定，  
由运行时在执行前解析：

```text
instance_id
→ 当前合法 crop
→ 当前合法 segmentation
→ 当前合法 measurement
```

---

## 4. 核心区别

| 维度 | 旧短计划 | 新 DAG |
|---|---|---|
| 生成者 | LLM 直接生成工具序列 | LLM 可生成语义目标/补丁；运行时编译执行节点 |
| 生成时机 | 观察之前 | 基于当前证据；执行前可重新解析 |
| 节点内容 | 具体工具 + target | 语义任务 + 条件 |
| target | 写死 crop/seg id | 执行时按实例和版本解析 |
| 候选绑定 | 候选名进入计划 | 候选只消费结果，不进入物理请求身份 |
| 失效处理 | 回退/拒绝旧计划 | 节点 `invalid_if`，立即停止或局部重规划 |
| 证据变化 | 计划容易过期 | 依赖版本变化只影响相关节点 |
| 并行 | 计划顺序执行 | 只并行独立工具，不并行提交证据 |
| 模型调用 | 计划一次，执行整段 | 只在关键事件/需要重规划时调用 |
| 停止 | 计划结束才收尾 | 事件驱动，可提前 review/final |
| 单写者 | 容易竞争 | 证据头只由 Single Writer 提交 |

## 5. 允许的 DAG

```text
1. 节点是语义任务，不是具体工具调用
2. target 在执行前解析
3. 每个节点有前置条件和失效条件
4. 关键证据变化时节点可失效
5. 可随时取消未开始节点
6. 不自动取消候选组
7. 不增加每 observation 一次 LLM
8. 不并行提交证据
```

示例：

```json
{
  "node_id": "measure_width",
  "semantic_task": "measure_width",
  "depends_on": ["identity", "mask", "eligibility"],
  "preconditions": [
    "identity.verified",
    "mask.quality=valid",
    "eligibility.width=true"
  ],
  "invalid_if": [
    "identity.rejected",
    "mask.review",
    "evidence_version changed"
  ]
}
```

---

## 6. 不允许的 DAG

```text
1. 模型一次生成 3–5 个具体工具调用
2. 节点写死 crop/seg target
3. 节点跨身份门预先规划 segment/measure
4. 计划生成后不重新检查合法性
5. 失败后继续执行旧计划的后续节点
6. DAG 完成后才允许 ReAct 决策
7. 用 DAG 完成自动替代 review/finish 判断
8. 因某个 GOAL_SATISFIED 自动取消候选组
9. 并行写 evidence head
10. 为每个节点单独调用 LLM
```

---

## 7. 停止与取消

```text
全局 stop：
  ReAct/LLM 决定 continue / review / finish
  运行时只校验 finish 资格
  没有合法动作时自动 review

候选组分支取消：
  ReAct/LLM 决定
  不能因 top1 required 满足自动取消

精确重复动作：
  运行时可以自动剪枝
  例如同一实例同一用途同一输入

节点失效：
  运行时可以自动 invalidate
  但不等同于取消竞争候选
```

---

## 8. 何时才值得引入 DAG

只有满足：

```text
1. 确实存在独立分支可并行
2. 确实存在可预见的局部依赖链
3. 运行时可解析 target
4. 有明确失效条件
5. 能减少实际 planning 请求
6. 不增加额外模型调用
7. A/B 证明优于单步 ReAct
```

否则：

```text
DAG 只是旧短计划的换名
```

---

## 9. 代码审查清单

看到“新增 DAG”时，逐条检查：

```text
[ ] 节点是否是语义任务，而不是固定工具调用？
[ ] target 是否在执行前解析？
[ ] 是否有 invalid_if？
[ ] 证据版本变化时是否只影响依赖节点？
[ ] 是否仍由 ReAct 决定调查目标和停止？
[ ] 候选组是否不会因局部目标满足被取消？
[ ] 是否只有 Single Writer 提交证据？
[ ] 是否避免每个 observation 调用 LLM？
[ ] 是否避免把候选名写进视觉请求？
[ ] 是否有真实 A/B，而不是只看代码结构？
```

---

## 10. 一句话

```text
旧短计划：
  模型在证据之前写死工具动作。

新 DAG：
  模型决定调查目标，
  运行时按当前证据编译语义节点并执行。

如果 DAG 由模型预先生成具体工具序列，
它就还是旧短计划，不应重新引入。
```
